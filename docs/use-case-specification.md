## 1. アクター

| アクター | 説明 |
|---|---|
| ユーザー | MobileとWearを所有し、設定・確認・承認を行う人 |
| Android OS | Mobileの電池状態、通知、ライフサイクル、再起動を管理する |
| Wear OS | Wearの通知、Tile、コンプリケーション、ライフサイクルを管理する |
| Google Play services | Wear Data Layerで状態とイベントを同期する |
| ウォッチフェイス | ユーザーが選択したコンプリケーションデータを描画する |

## 2. UC-001 初期設定する

**事前条件**: Mobileアプリがインストールされている。  
**トリガー**: ユーザーが初回起動する。

### 基本フロー

1. アプリは機能と継続監視の必要性を説明する。
2. ユーザーは通知しきい値を確認または変更する。
3. アプリは通知を行う理由を説明して通知権限を要求する。
4. ユーザーは「監視を開始」を選択する。
5. アプリはForeground Serviceを開始し、現在の電池状態を保存する。
6. アプリはWearとの接続状態とセットアップ案内を表示する。

### 代替フロー

- 3a. 権限拒否: 設定は続行できるが、通知不可を明示し、システム設定への導線を出す。
- 4a. 後で設定: 監視は開始せず、ホームに未監視状態を表示する。
- 5a. FGS開始失敗: エラーを記録し、ユーザー操作から再試行できる状態へ戻す。

**事後条件**: 設定が永続化され、選択に応じて監視が稼働する。  
**受け入れ条件**: AC-001、AC-012。

## 3. UC-002 しきい値を変更する

**事前条件**: Mobileアプリを操作できる。  
**トリガー**: ユーザーが設定画面を開く。

1. 現在のしきい値を表示する。
2. ユーザーが5～100%から値を選択する。
3. 保存時に範囲を検証し、DataStoreへ原子的に保存する。
4. 現在の電池状態を新しいしきい値で評価する。
5. 新しい設定と状態をWearへ同期する。

しきい値変更そのものでは低残量通知を発生させない。現在値以下へしきい値を引き上げた場合は「現在すでに設定値以下」と画面表示し、次の再アーム後から通知する。

## 4. UC-003 低残量通知を受け取る

**事前条件**: 監視中で、前回残量がしきい値より大きい。  
**トリガー**: 現在残量がしきい値以下になる。

1. Mobileは到達条件と再アーム状態を判定する。
2. 新しい`ThresholdReachedEvent`を生成・保存する。
3. Mobile通知権限があればMobile通知を出す。
4. 状態DataItemと通知イベントDataItemをurgentで送信する。
5. Wearはイベントを検証し、未処理かつ期限内ならWear通知を出す。
6. 両端末はeventIdを処理済みとして記録する。

**例外**:

- 通知権限なし: 通知を省略するがイベントと同期は維持する。
- Wear切断: Mobile通知のみ行い、再接続時にイベント期限を検証する。
- 同一イベント再受信: 破棄する。

**受け入れ条件**: AC-002、AC-003、AC-007。

## 5. UC-004 Wearで状態を確認する

**事前条件**: Wearアプリがインストールされている。  
**トリガー**: ユーザーがWearアプリまたはTileを開く。

1. WearはローカルDataStoreの直近正常値を即座に表示する。
2. 現在時刻と受信時刻からFresh/Delayed/Staleを判定する。
3. 到達可能なMobile nodeがあれば状態更新を要求する。
4. 新しい正常データ受信後、表示、Tile、コンプリケーションを更新する。

**例外**:

- データなし: ペアリングと両アプリのインストールを案内する。
- Stale: 最終値、警告、最終更新時刻、再試行を表示する。
- 異常データ: 直前の正常値を保持し、診断カウンタのみ更新する。

## 6. UC-005 ウォッチフェイスへ追加する

1. ユーザーがコンプリケーション対応ウォッチフェイスの編集画面を開く。
2. 対応スロットを選び、Battery Notifierをデータソースとして選択する。
3. ウォッチフェイスが要求した型に応じて百分率を表示する。
4. ユーザーがコンプリケーションをタップするとWearアプリが開く。

ウォッチフェイスがコンプリケーション非対応、または対応型を持たない場合は追加できない。アプリが他社ウォッチフェイスのレイアウトを変更することはない。

## 7. UC-006 切断と再接続から復旧する

1. Wearとの接続が失われてもMobileは監視を継続する。
2. Mobileは固定状態DataItemを最新値で上書きする。
3. Wearは経過時間に応じてDelayed/Staleを表示する。
4. 再接続時、Mobileは現在値を再取得し、新しいsequenceでurgent送信する。
5. Wearは古いsequenceを無視し、最新値を保存する。
6. 有効期限切れの通知イベントは通知せず処理済みにする。

**受け入れ条件**: AC-005、AC-006、AC-007。

## 8. UC-007 再起動後に復旧する

### Mobile再起動

1. BootReceiverは監視有効設定を確認する。
2. OS制約上開始可能なら監視FGSを復元する。
3. 開始できない場合は再開を促す通知または次回起動時の案内を設定する。
4. 現在状態を取得し、DataStoreとData Layerを更新する。

### Watch再起動

1. WearはDataStoreの直近値を読み込む。
2. 鮮度を再計算し、古い値をFreshとして扱わない。
3. Tile/コンプリケーション要求時に保存値を返し、Mobileへ更新要求を送る。

## 9. UC-008 監視を停止する

1. ユーザーがMobile画面またはongoing通知の「停止」を選ぶ。
2. Mobileは監視設定を無効にし、ReceiverとFGSを停止する。
3. 監視停止状態をWearへ同期する。
4. Wearは残量を表示できる場合も「監視停止中」と明示し、新規通知を行わない。

## 10. UC-009 Wearからしきい値変更を要求する（BN-002提案）

**事前条件**: Wearに最後の正常なMobile stateがあり、対応Mobile capabilityを確認できる。
**トリガー**: ユーザーがWearのしきい値編集画面を開く。

### 基本フロー

1. WearはMobileから最後に確認した有効しきい値を表示する。
2. ユーザーは5～100%から1%単位で下書きを変更する。
3. Wearは明示的な保存操作で`requestId`、要求値、期待値をProto DataStoreへ保存する。
4. Wearは接続中の対応Mobile nodeへ変更要求messageを送る。
5. Mobileはpayloadを完全検証し、期待値と現在値を比較する。
6. Mobileは既存の設定変更処理で値、alert state、state sequence、同期outbox、要求結果を原子的に保存する。
7. Mobileは要求元へ結果を返し、新しいphone-stateを送る。
8. Wearは結果とphone-stateの収束を確認して適用済みを表示する。

### 代替・例外フロー

- 4a. 切断/送信失敗: 有効値を変更せず未保存と表示し、下書きと同じ`requestId`を保持する。再接続だけでは送らず、ユーザーの再試行を待つ。
- 5a. 期待値競合: Mobileは変更せず`CONFLICT`と現在値を返す。Wearは現在値を表示して新しい編集を促す。
- 5b. 不正/未対応payload: Mobileは設定を変更せず診断へ記録する。安全に照合できる要求だけ`REJECTED`を返す。
- 7a. Mobile適用後に結果喪失: Wearは結果不明を表示する。同じ`requestId`の再試行にMobileが保存済み結果を返し、設定を再適用しない。
- 8a. Wear再起動: 下書きと未確定状態を復元するが自動送信しない。

**事後条件**: Mobileだけが有効設定を永続化し、Wearはphone-stateを表示の正本とする。
**受け入れ条件**: AC-015、AC-016、AC-017。
